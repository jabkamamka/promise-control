# Подключение к API УралМикро

Проверено на живом API 29.10.2026: `GET /api/v1/operators` → 200, `GET /api/v1/calls` → 200 `[]`.
Ниже — что делать с токеном и почему список звонков может быть пустым при рабочем токене.

## 1. service_token выдаётся команде, а не участнику

В Swagger УралМикро: **POST /teams** → Try it out → тело:

```json
{"name": "название-команды"}
```

→ Execute. Успех — **201**, в ответе `id`, `name`, `service_token`, `created_at`.
Токен нужно сохранить сразу: повторно API его не отдаёт, при потере — только через
представителя УралМикро.

Проверенные ответы:

| Ситуация | Ответ |
|---|---|
| Новая команда | `201` + `service_token` |
| Имя уже занято | `409` `{"message":"team already exists"}` |
| Имя с пробелом (`"DOta Team"`) | `400` `{"message":"invalid request body"}` — используйте дефис |
| Без токена в запросе | `401` `{"message":"missing service token"}` |

Один токен — на команду. `access_token` оператора (получается через `/auth/*`) —
другой токен и для других действий; в заголовке `X-Service-Token` он не подходит.

## 2. Куда его подставлять

В Swagger — кнопка **Authorize** сверху, поле `ServiceToken`, токен **без** слова
`Bearer`, затем Authorize и Close.

В коде и в `curl` — заголовок:

```powershell
curl.exe "https://utmn-api.uralmicro.ru/api/v1/operators" -H "X-Service-Token: ТОКЕН"
```

Ответ `200` даже с пустым списком `{"items":[],"total":0}` означает, что токен принят.
Заголовок `Authorization: Bearer ...` с этим токеном даёт `401`.

## 3. Почему `GET /calls` пустой, хотя токен рабочий

Звонок достаётся оператору, у которого в момент начала звонка идёт смена в его
часовом поясе. Если у команды нет операторов, отдавать нечего — приходит `[]` с кодом 200.

Публичного метода создания операторов нет: `POST /api/v1/operators` → `405`,
`Allow: GET`. Операторов заводит организатор. Поэтому пустой `/calls` — это не
ошибка токена, а отсутствие операторов на стороне платформы.

## 4. Формат звонка от программы-отправителя

Схема снята с бинарника `sender_windows_amd64.exe` (JSON-теги Go-структур) и
подтверждена корпусом `data/sample_calls.json`:

```json
{
  "id": "call-0001",
  "operator_id": 101,
  "client_phone": "+7 912 345-67-89",
  "started_at": "2026-10-29T14:52:00+05:00",
  "ended_at": "2026-10-29T14:58:00+05:00",
  "transcript": [
    {"speaker": "оператор", "text": "Я перезвоню вам через час."},
    {"speaker": "клиент", "text": "Хорошо, спасибо."}
  ]
}
```

Важные детали:

- `operator_id` — **число** (`int64`). Строка приводит к ошибке декодирования в
  отправщике: `json: cannot unmarshal string into Go struct field ... operator_id of type int64`.
- телефон лежит в `client_phone`, а не в `phone`;
- реплики — `transcript` с полями `speaker` (`оператор` / `клиент`) и `text`;
- сервис принимает и массив звонков, и обёртку `{"calls": [...]}`.

## 5. Проверка отправщика без доступа к API организаторов

`tools/mock_api.py` отдаёт корпус из `data/sample_calls.json` в этой же схеме:

```powershell
python tools\mock_api.py 8099
.\sender_windows_amd64.exe -t test-token -w http://localhost:8080/webhook/calls -a http://127.0.0.1:8099
```

Отправщик заберёт звонки и отправит их на вебхук — так проверяется совместимость
с настоящим бинарником, не завися от того, выдала ли платформа операторов.

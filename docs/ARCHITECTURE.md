# Архитектура

## Задача

Из готовой расшифровки звонка найти обещания **оператора** и превратить каждое в задачу со сроком,
чтобы обещание не потерялось. Минимальный уровень кейса: приём звонков, три типа обещаний,
сроки, статусы, фильтры, защита от дублей, API для добавления новых типов.

## Поток данных

```
sender_windows_amd64.exe
        │  POST /webhook/calls  (10 звонков в массиве, каждые 30 секунд)
        ▼
app/api/calls.py            валидация запроса, X-Webhook-Token (опционально)
        ▼
app/services/ingest.py      нормализация, идемпотентность, запись в SQLite
        ▼
app/services/detect.py      поиск обещаний в репликах оператора
        ├── app/services/taxonomy.py   типы, глаголы, объекты, адресаты
        └── app/services/deadline.py   «завтра до обеда» → 2026-10-30T07:00:00Z
        ▼
app/services/tasks.py       задачи, статусы, просрочка, фильтры, статистика
        ▼
app/api/tasks.py, types.py, system.py   HTTP-слой
        ▼
app/web/                    панель оператора (ванильный JS)
```

## Слой поиска обещаний (detect.py)

### 1. Только оператор

Реплики клиента не анализируются: «Я пришлю вам фото» — это не обязательство компании.
Допустимые значения `speaker`: `operator`, `оператор`, `op`, `manager`, `agent`, `специалист`.

### 2. Сегментация

Реплика режется по знакам конца предложения. Один звонок в данных кейса содержит 3–6 вопросов,
каждый — отдельная реплика оператора, поэтому «несколько обещаний в звонке» естественно дают
несколько задач.

### 3. Признак обещания

Ищется глагол в **1-м лице будущего времени совершенного вида**: `перезвоню`, `отправлю`, `уточню`,
`передам`, `напомню`. Формы перечислены явно (`taxonomy.VERBS`), поэтому:

- прошедшее время («перезвонил») не ловится;
- инфинитив («могу перезвонить») не ловится;
- вопросы отсекаются отдельно (`?` в конце или вопросительное слово в начале);
- сослагательное наклонение («если бы», «могли бы») отсекается;
- отрицание перед глаголом («не буду гадать, … уточню») отсекается по контексту слова.

### 4. Тип обещания

Тип = что именно оператор обязался сделать. Приоритеты нужны, когда в одной реплике несколько
действий: побеждает то, что клиент увидит сам.

| Код | Приоритет | Смысл |
|---|---|---|
| `documents` | 90 | отправить документы (счёт, акт, справка, договор, КП, каталог…) |
| `clarification` | 85 (88 при «уточню + вернусь с ответом») | уточнить и вернуться с ответом |
| `callback` | 80 | перезвонить клиенту |
| `visit` | 60 | организовать выезд мастера |
| `fix` | 50 | исправить данные, пересчитать, оформить возврат |
| `transfer` | 40 | передать обращение руководителю/в склад/в логистику |
| `notification` | 30 | напомнить смс/уведомлением |

Уточнение типа идёт по объекту и адресату:

- «пришлю **смс**» без документа → `notification`;
- «направлю **вам на согласование** договор» → `documents`;
- «оформлю **повторный выезд**» → `visit`.

Если в реплике несколько действий разного типа («Передам заявку на склад **и наберу вас в четверг**»),
задача одна: тип по приоритету (`callback`), все действия — в `actions`, второй тип — в `secondary_types`.

### 5. Пользовательские типы

Тип, добавленный через `POST /api/v1/promise-types`, участвует в конкуренции за реплику:

- `keywords` — подстроки-стемы (`скидк` → «скидку»);
- `description` и `examples` — мешок слов для пересечения с репликой;
- приоритет = базовый (78) + 4 за каждое ключевое слово (максимум 3) + 2 за хорошее пересечение.

Новый тип применяется к новым звонкам. Для старых: `POST /api/v1/calls/{id}/reanalyze` —
повторный прогон без дублей.

## Слой сроков (deadline.py)

Срок считается **от `ended_at` звонка** в часовом поясе `APP_TIMEZONE`.
Порядок разбора (первое совпадение выигрывает):

1. «до конца рабочего дня», «в течение дня», «до конца недели/месяца», «на следующей неделе», «на днях»;
2. «через …» / «в течение …»: минуты, часы, дни, **рабочие** дни, недели (диапазон «два-три дня» → берём максимум);
3. «сегодня / завтра / послезавтра» + время суток;
4. день недели («в четверг», «до пятницы», «в среду утром») — ближайший будущий;
5. абсолютная дата («5 ноября», «05.11»);
6. только время суток («до обеда» → 12:00, «после обеда» → 15:00, «около шести» → 18:00);
7. «прямо сейчас» / «сейчас» → +15 минут;
8. иначе — 24 часа (`default_24h`).

Время суток понимает и цифры, и слова: «в десять утра» = 10:00, «до двенадцати» = 12:00,
«часа в два» = 14:00. Если посчитанный срок уже в прошлом — он сдвигается на час вперёд,
источник помечается `clamped` (задача не должна быть просроченной в момент создания).

Фраза, по которой посчитан срок, сохраняется в `due_hint` — на защите и в интерфейсе видно,
почему дедлайн именно такой.

## Данные (SQLite)

```
calls           id, operator_id, client_phone, started_at, ended_at, transcript(JSON),
                received_at, processed_at, promise_count, status, raw(JSON)
promise_types   code, title, description, keywords(JSON), examples(JSON),
                is_builtin, priority, created_at, updated_at
tasks           id, call_id→calls, operator_id, promise_type→promise_types, title, object,
                quote, transcript_index, actions(JSON), secondary_types(JSON),
                due_at, due_hint, deadline_source, status, confidence, matched_by,
                created_at, updated_at, closed_at, overdue_marked_at, dedupe_key (UNIQUE),
                search_text
task_events     id, task_id→tasks, event, from_status, to_status, comment, at
```

Почему так:

- **`dedupe_key` (UNIQUE)** — защита от дублей на уровне БД, а не в коде: `INSERT … ON CONFLICT DO NOTHING`.
  Ключ = sha1(`call_id` + тип + индекс реплики + нормализованный текст).
- **`calls.id` — первичный ключ**: повторный приём того же звонка вообще не доходит до детектора.
- **`quote` + `transcript_index`** — любую задачу можно проверить по исходной реплике (кнопка «звонок» в UI).
- **`search_text`** — предпосчитанная нормализованная строка для поиска (SQLite `lower()` не умеет кириллицу).
- **`task_events`** — аудит: создание, смены статуса, автоматическая просрочка. Нужен для разбора
  «почему задача просрочена» и для будущей проверки исполнения.

## Статусы и просрочка

В БД только три статуса: `created`, `in_progress`, `done`. Разрешённые переходы — в `tasks.TRANSITIONS`:

```
created → in_progress → done
              ↑            │
              └────────────┘  (вернуть в работу)
```

Просрочка — **вычисляемое** состояние: `due_at < now AND status != done`. При чтении API:

1. `mark_overdue()` проставляет `overdue_marked_at` и пишет событие `overdue` (идемпотентно);
2. `effective_status` = `overdue` для отдачи наружу.

Так «Выполнена» никогда не станет «Просрочена», а фильтр `status=overdue` работает без фонового процесса.
При этом фильтры `created`/`in_progress` исключают просроченные задачи, чтобы списки не путали оператора.

## Идемпотентность и устойчивость

- Батч обрабатывается по одному звонку в отдельной транзакции: битый звонок не ломает остальные.
- Ответ вебхука возвращает `processed / duplicates / failed / tasks_created`.
- Ошибка сохранения откатывает транзакцию звонка, но не батча.

## Веб-панель

`app/web` — один HTML + CSS + JS без сборки и зависимостей. Умеет: фильтры по статусу/типу,
поиск, пагинацию, смену статуса, просмотр расшифровки с подсветкой реплик-обещаний,
просмотр и добавление типов. Часовой пояс для отображения берётся из `/health`.

## Что осознанно не сделано

| Не сделано | Почему |
|---|---|
| Проверка исполнения по следующим звонкам | Кейс разрешает не делать на минимальном уровне |
| Полноценная семантика/эмбеддинги | Нужна работа офлайн и объяснимость; лексика + правила дают предсказуемый результат |
| PostgreSQL, очередь, несколько воркеров | Демо-нагрузка — десятки звонков; схема готова к переезду |
| Аутентификация операторов | Кейс требует только API; для продакшена нужен OAuth/токен оператора |
| Праздничные дни | Нужен производственный календарь РФ |

## Точки расширения

1. **Проверка исполнения**: сопоставить задачу со следующими звонками клиента (`client_phone`),
   искать подтверждение/опровержение в репликах.
2. **Эмбеддинги**: заменить лексическое пересечение в `_custom_candidates` на косинусную близость,
   контракт `PromiseType` уже содержит описание и примеры.
3. **Уведомления**: `notify_channel` у оператора в API партнёра — точки для Telegram/MAX.
4. **Мультитенантность**: `team_id` в звонках и задачах (сейчас команда одна).

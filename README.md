# Сервис контроля обещаний

Прототип для кейса УралМикро (хакатон 2026): сервис принимает расшифровки звонков
контакт-центра, находит в репликах оператора обещания («перезвоню», «вышлю счёт»,
«уточню и вернусь с ответом»), превращает каждое обещание в задачу со сроком и
ведёт её до закрытия. Просроченные задачи сервис помечает сам.

Что умеет:

- принимает пачку звонков на вебхук и повторную обработку того же звонка не превращает в дубли;
- находит три стартовых типа обещаний и позволяет добавить новый тип через API по смысловому описанию;
- каждое обещание — отдельная задача, даже если в одном звонке их несколько;
- считает срок относительно окончания звонка, а если срок не назван — ставит +24 часа;
- ведёт статусы «Создана → В работе → Выполнена» и сам выставляет «Просрочена»;
- отдаёт задачи с фильтрами по статусу, сроку, оператору, типу и звонку;
- показывает простую панель оператора (веб-интерфейс не обязателен по кейсу, но удобен для демонстрации).

## Быстрый старт на Windows

Нужен Python 3.11 или новее (проверено на 3.13).

```powershell
cd promise-service
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Если PowerShell не разрешает активацию окружения, выполните один раз
`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` или запускайте
`.\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8000` без активации.

После запуска:

- панель оператора — <http://127.0.0.1:8000/dashboard>
- Swagger с методами API — <http://127.0.0.1:8000/docs>
- проверка живости — <http://127.0.0.1:8000/health>

База — SQLite в `data/promises.db`, создаётся автоматически при первом запуске.
Файл можно удалить, чтобы начать с чистого листа.

## Подключение программы-отправителя

1. Создайте команду и получите `service_token`:

```powershell
curl.exe -X POST "https://utmn-api.uralmicro.ru/api/v1/teams" `
  -H "Content-Type: application/json" -d '{\"name\":\"my-team\"}'
```

2. Запустите сервер (см. выше) и отправщик:

```powershell
.\sender_windows_amd64.exe -t <service_token> -w http://localhost:8000/webhook/calls
```

Отправщик раз в 30 секунд забирает до 10 звонков из API и делает POST на вебхук.
Сервис принимает как массив звонков, так и обёртку `{"calls": [...]}`.

## Демонстрация сквозного сценария

В отдельном окне при запущенном сервере:

```powershell
cd promise-service
python demo\run_demo.py
```

Скрипт проходит путь целиком, как на защите:

1. отправляет 10 синтетических звонков на `POST /webhook/calls` (11 задач);
2. повторно отправляет те же звонки и показывает, что дублей нет;
3. выводит список задач с типом, статусом, сроком и цитатой;
4. переводит задачу в «В работе» и закрывает её;
5. показывает автоматически просроченные задачи;
6. фильтрует задачи по оператору;
7. добавляет новый тип обещания через `POST /promise-types` и находит задачу нового типа;
8. печатает сводку `GET /stats`.

Время звонков в демо сдвигается к текущему моменту, поэтому сценарий не устаревает:
свежие звонки дают задачи в будущем, а один звонок двухдневной давности — просроченные.

## API

Базовый адрес — `http://127.0.0.1:8000`. Полная схема — `/docs`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/webhook/calls` | Приём массива звонков от отправщика; возвращает отчёт по каждому звонку |
| POST | `/calls` | То же самое, если отправщик настроен на `/calls` |
| GET | `/calls` | Список принятых звонков (limit/offset) |
| GET | `/calls/{call_id}` | Звонок, его расшифровка и созданные задачи |
| POST | `/calls/{call_id}/reprocess` | Повторный разбор: добавляет только недостающие задачи |
| GET | `/tasks` | Задачи с фильтрами (см. ниже) |
| GET | `/tasks/{id}` | Задача и история смены статусов |
| PATCH | `/tasks/{id}/status` | Смена статуса: `in_progress`, `done` |
| POST | `/tasks/{id}/status` | То же, если клиент умеет только POST |
| GET | `/promise-types` | Справочник типов обещаний |
| POST | `/promise-types` | Новый тип по смысловому описанию |
| PATCH | `/promise-types/{code}?active=false` | Включить/выключить тип (встроенные не отключаются) |
| GET | `/stats` | Сводка: звонки, задачи, распределение по статусам и типам |
| GET | `/health` | Проверка живости |

Фильтры `GET /tasks`: `status` (`created,in_progress,done,overdue`, можно списком),
`operator_id`, `type_code`, `call_id`, `due_before`, `due_after`, `overdue=true`,
`q` (поиск по заголовку и цитате), `sort` (`due_at`, `-due_at`, `created_at`, …),
`limit` (до 500), `offset`.

Примеры:

```powershell
# задачи в работе у конкретного оператора, ближайшие сверху
curl.exe "http://127.0.0.1:8000/tasks?status=in_progress&operator_id=op-anna&sort=due_at"

# новая задача в работу
curl.exe -X PATCH "http://127.0.0.1:8000/tasks/1/status" `
  -H "Content-Type: application/json" -d '{\"status\":\"in_progress\",\"note\":\"Беру в работу\"}'

# свой тип обещания
curl.exe -X POST "http://127.0.0.1:8000/promise-types" -H "Content-Type: application/json" -d '{
  \"name\": \"Переключить на отдел\",
  \"description\": \"Оператор обещает соединить клиента с профильным специалистом.\",
  \"keywords\": [\"переключу\", \"соединю\"]
}'
```

## Как сервис находит обещания

Решение полностью объяснимое и работает без внешних сервисов:

1. **Только реплики оператора.** Обещание клиента задачей не становится: в демо-звонке
   `demo-0010` клиент говорит «я вам перезвоню», и сервис не создаёт задачу.
2. **Разбиение на смысловые куски.** Предложение делится по запятым и союзам
   («перезвоню через час **и** отправлю договор завтра в 10:00» → две задачи с разными сроками).
3. **Шаблоны и опорные слова** по каждому типу: «перезвоню/позвоню/наберу»,
   «вышлю/отправлю/пришлю + документ/счёт/договор», «уточню/выясню/проверю +
   вернусь с ответом». Морфология — грубый стеммер и сравнение основ, поэтому
   «уточнить», «уточню», «уточнит» попадают в один тип.
4. **Отрицания отбрасываются**: «не перезвоню», «не смогу», «вряд ли».
5. **Осторожные обещания сохраняются, но с меньшей уверенностью**: «постараюсь
   уточнить» создаёт задачу с `confidence` ниже.
6. **Одно предложение — одно обещание одного типа.** Два разных обещания одного
   типа в разных предложениях остаются двумя задачами.

Новый тип добавляется через `POST /promise-types`: достаточно названия, смыслового
описания и списка опорных слов (или регулярных выражений). Тип сразу участвует в
разборе следующих звонков.

## Сроки

Срок ищется в том же смысловом куске, где прозвучало обещание; если его там нет —
в следующих репликах оператора. Поддерживаются:

- «через 15 минут», «через час», «через полчаса», «через два дня», «через неделю»;
- «в течение часа», «в течение двух рабочих дней» (рабочие дни считаются без выходных);
- «сегодня до 18:00», «завтра в 10:00», «послезавтра», «до конца дня/недели/месяца»;
- «в понедельник в 11:00» (ближайший будущий день недели);
- «12.11.2026 в 14:30», «12 ноября».

Если срок не назван — ставится +24 часа от окончания звонка, в задаче это
помечено `due_source: "default"` и текстом «срок в разговоре не назван».
Наивные даты трактуются в часовом поясе звонка; в базе всё хранится в UTC.

## Статусы

`Создана → В работе → Выполнена`. Статус «Просрочена» выставляется автоматически,
когда срок прошёл, а задача не закрыта: проверка идёт фоновой задачей каждые 30
секунд и дополнительно при каждом чтении списка задач. Вручную поставить
«Просрочена» нельзя (409), история переходов доступна в `GET /tasks/{id}`.

## Защита от дублей

- Звонок хранится по уникальному `id`: повторная отправка того же звонка
  возвращает `duplicates: 1` и не создаёт задач.
- Даже при повторном разборе (`POST /calls/{id}/reprocess`) задачи вставляются
  по уникальному ключу `(call_id, dedupe_key)`, где ключ — тип + нормализованная
  цитата. Новые типы добавят только недостающие задачи, старые не размножатся.

## Структура проекта

```
promise-service/
├── app/
│   ├── main.py          # FastAPI: маршруты, фоновая проверка просрочек
│   ├── service.py       # бизнес-логика: приём звонков, задачи, статусы, фильтры
│   ├── detector.py      # поиск обещаний, встроенные и пользовательские типы
│   ├── datetime_ru.py   # разбор сроков из русской речи
│   ├── calls.py         # терпимый разбор входящего payload
│   ├── text.py          # нормализация, стеммер, разбиение на предложения
│   ├── db.py            # SQLite: схема, подключение, сериализация
│   └── config.py        # настройки через переменные окружения
├── tests/               # 28 тестов: сроки, поиск обещаний, API
├── demo/                # 10 демонстрационных звонков и сквозной сценарий
├── static/dashboard.html
├── requirements.txt
└── README.md
```

Хранение — SQLite (файл `data/promises.db`), без ORM и внешних сервисов: прототип
запускается на школьной Windows-машине одной командой.

## Тесты

```powershell
cd promise-service
python -m pytest -q
```

Покрыто: разбор сроков (12 тестов), поиск обещаний и роли (8), API и сквозные
сценарии (8): идемпотентность вебхука, фильтры, переходы статусов, автоматическая
просрочка, добавление нового типа, сводка, некорректный payload.

## Ограничения

- Поиск обещаний — правила и опорные слова, а не языковая модель. Сарказм,
  сложные перефразирования и длинные рассуждения могут не распознаться: в спорных
  случаях сервис лучше промолчит, чем создаст ложную задачу.
- Нет автоматической проверки, выполнено ли обещание по последующим звонкам
  (по кейсу это не требуется на минимальном уровне).
- Нет уведомлений и авторизации: API открыт внутри доверенного контура, как в
  прототипе; для продакшена нужны токены, HTTPS и ограничение CORS.
- Дубли определяются по `id` звонка; если источник присылает один и тот же
  разговор с разными `id`, сервис воспримет их как разные звонки.
- SQLite и один процесс: горизонтальное масштабирование не реализовано
  (по кейсу это разрешено не делать).

## Использованные ИИ-инструменты

- **Claude (AutoClaw)** — генерация кода, тестов, текста README и разбор
  расшифровки голосовой записи; все решения проверены запуском тестов и сквозного
  сценария.
- **faster-whisper (модель small)** — локальная расшифровка записи организаторов,
  внешние сервисы распознавания не использовались.
- Логика поиска обещаний и расчёта сроков написана как обычные правила — без
  обращений к LLM во время работы сервиса, поэтому результат воспроизводим и
  объясним на защите.
